# gendock maintenance

Read `../../../docs/architecture.md` and `../../../AGENTS.md`, relative to this skill directory. Read `references/pitfalls.md` for established failure cases.

1. Identify the implemented behavior and its public CLI or storage contract. Mark planned work explicitly.
2. Trace ownership: who owns a file, database row, runtime and subprocess? External weights belong to their owner and must remain untouched.
3. Resolve all application paths through `Paths`. Test custom absolute XDG roots and ignored relative roots without changing process-wide environment in parallel tests.
4. Before 1.0, edit the single `migrations/001_initial.sql` schema snapshot; do not add incremental scripts. Initialize only empty databases and reject incompatible schemas without data deletion/reset. Current compatible development DBs must keep working. After 1.0, introduce transactional versioned migrations for released user databases. Keep built-in model data revisions separate from schema versions. For queue changes, test independent connections and failure recovery rather than just in-memory state.
5. For backend work, choose a private runtime by absolute path. No ambient Python discovery. Keep downloads, native dependency compatibility and cancellation explicit.
6. Validate with formatting, clippy and locked tests. Exercise the CLI under temporary XDG roots, including help/version, parsing errors and side-effect-free stubs. Operations return JSON without `--json`; help-only invocations print text and exit 0. Successful foreground service execution streams leveled console logs; startup failures remain JSON. Test default foreground, --daemon and launchd registration independently, and preserve concrete child startup errors. `cargo test` reports pass/fail, not line coverage; use cargo-llvm-cov separately and report only measured coverage. Never use real models for routine unit tests.
7. Error contracts follow `../../../docs/json-contract.md`: stable codes, structured details and next_steps, no rendered terminal help in strings. JSON newline escaping itself is correct; do not remove legitimate newlines from generated/user content.
8. For model management, read `../../../docs/models.md`. Pin revisions and hashes; retain valid partial downloads; activate/register only after verification. Endpoint selects a repository origin; proxy configures networking. Search/info query SQLite and may initialize it and reconcile versioned seeds; they do not fetch remote metadata or weights. User manifests always have user origin and must never overwrite built-in definitions. Built-in lifecycle upgrades cannot delete files or revert newer catalog revisions. Direct R2/CDN file URLs bypass HF endpoint rewriting. Never send an official HF token to a mirror.
9. For image execution, read `../../../docs/image-generation.md`. Keep engines hidden from normal CLI inputs, use registered private executables, validate model/output data, capture logs away from stdout, record resolved parameters and assets, and test cancellation/ownership/export races. Defaults export to the invocation directory as local-time image_MMDD_HHMM.png with atomic collision suffixes; explicit --out conflicts fail and managed assets remain archived. Never treat mock-worker tests as real inference validation; keep a separate real smoke check.
10. Image model defaults come from XDG config.toml, independently for generate/edit; never silently replace user configuration or auto-download on execution. Editing validates and snapshots input bytes, records provenance and invokes the registered edit component. Test config overrides, unavailable models, original preservation and correct operation kinds.
11. Update `../../../docs/features.md` in the same change whenever implementation, availability or supported scope changes. It is the canonical feature table: status, readiness percentage, evidence, blockers and next step. Percentages are scoped estimates, not coverage; 60% is basically usable, 100% requires complete scoped acceptance, and stubs stay 0%. Keep product positioning focused on curated local AI capabilities for nontechnical users and agents.
12. For service work, read `../../../docs/server.md` and `../../../docs/testing.md`. Reuse job JSON and existing execution IDs, enforce transactional pending limits and fenced single-worker claims, check cancellation/heartbeats during model hashing, and reconcile orphans only under the image lock. Never steal GPU work based only on lease expiry or kill an unverified PID. Preserve queue state on shutdown; interrupted work is not automatically replayed. Validate ownership for uploads/results and keep server paths out of remote replies. SSE reconnect delivers current persisted state, not historical replay.
13. User workflows require chained CLI E2E scripts. Routine `scripts/e2e.sh` uses tiny private workers; real `scripts/e2e-real.sh` is explicit, release-built, read-only against existing weights/runtime and isolated in temporary host/client XDG roots. Verify actual PNG content, unchanged originals and client independence; retain inspectable artifacts and do not equate mock success with model quality.
14. Service registration uses launchd label gendockd with an XDG canonical plist and an OS-required LaunchAgents symlink. Carry only explicit HOME/XDG roots and a service marker; never place credentials in the plist. Serialize mutations, preserve foreign files and roll back failed new registrations. Routine tests mock launchctl; the explicit launchd_live test checks real bootstrap/status/unregister under temporary HOME and refuses existing jobs.
15. Update capability documentation and add only durable, reproducible lessons to the pitfalls reference.

Do not publish, upload, send messages or download models as part of this skill. It requires no special approval for normal local development.
